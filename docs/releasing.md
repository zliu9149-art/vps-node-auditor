# 公开发布与命名

## 名称分层

本项目使用三层名称，避免把 GitHub 可识别性和终端输入长度绑在一起：

| 层级 | 名称 | 用途 |
|---|---|---|
| 正式项目名 | VPS Node Auditor | README、GitHub 标题、Release 和文档 |
| 仓库名 | `vps-node-auditor` | URL、克隆和包来源 |
| 日常命令 | `vna` | VPS 上高频交互 |

`node-audit`、`node-provision`、collector 和 systemd unit 是兼容或内部名称，不要求初学者记忆。未来若采用品牌名，只改展示层；稳定命令 `vna` 和配置目录不应随营销名称频繁变化。

## 命令长度与易用性

输入长度是易用性的一个指标，但不是决定性指标。更重要的是：

1. 是否只有一个清晰入口；
2. 子命令和参数能否从语义猜出；
3. 默认行为是否安全；
4. 错误是否说明下一步；
5. 是否避免分页器、时区和历史日志等意外行为；
6. 是否能通过 `help` 自助发现功能；
7. 脚本接口是否稳定。

因此项目选择三字符入口 `vna`，但不增加 `s`、`u`、`c` 等难以发现的单字母子命令。`vna create --user home --device phone` 比更短但含义模糊的命令更容易长期记忆。

## 版本策略

正式发布使用语义化版本：

- `v0.1.0`：首次公开预览，接口仍可能调整；
- `v0.x.y`：公开测试阶段；
- `v1.0.0`：CLI、配置和数据库升级承诺稳定。

构建 Release 时注入版本号：

```bash
go build -trimpath -buildvcs=false \
  -ldflags "-X main.version=v0.1.0" \
  -o dist/linux-amd64/vna ./cmd/vna
```

用户可运行 `vna version` 核对安装版本。

## GitHub 公开前检查

当前代码可以继续准备公开发布，但在创建公开仓库或 Release 前必须完成：

- 由项目所有者明确选择许可证；不要在 MIT、Apache-2.0、GPL 等许可证之间替用户决定；
- 对完整 Git 历史和当前文件执行秘密扫描，确认没有真实 IP、UUID、密钥、SNI、short ID、数据库或私有 YAML；
- 增加 CI，至少运行 `gofmt` 检查、`go vet ./...`、`go test ./...` 和 Linux AMD64 构建；
- 为每个发布资产提供 SHA-256 清单；
- 从干净标签构建，不直接上传开发机上来源不明的旧产物；
- 在 Release Notes 中写明支持的发行版、sing-box 构建要求、升级和回滚方法；
- 将真实部署信息继续限制在 Git 忽略且权限受控的服务器文件中；
- 在公开前再次确认引用项目的许可证和归属说明。

正式名称不需要听起来像商业品牌。对这一类小型管理员工具，清楚说明用途、搜索容易、没有名称冲突，通常比生造名称更重要。发布前仍应在 GitHub、主流软件包仓库和搜索引擎中检查 `VPS Node Auditor` / `vna` 的名称占用和潜在冲突。
